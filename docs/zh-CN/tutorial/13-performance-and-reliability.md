# 13 性能与可靠性

## 本章学习目标

清晰剥离指令准备、图层合成、数据输出与视口呈现的各阶段开销；为不同目标选用最合适的基准测试工具；并学会为受信任环境与受限输入环境合理配置预算。
基础预算示例无需开启任何可选特性。性能基准测试根据所测工作负载按需启用 `text`、`particles`、`gpu` 或原生编解码器环境。

## 最小可运行示例：显式工作量配额控制

```rust,no_run
use motion::prelude::*;
use motion::render::RasterLimits;

fn main() -> motion::Result {
    let timeline = Timeline::new(Size::new(320.0, 180.0), fps!(30)).track(|track| {
        track.scene(1.seconds(), |context| {
            context.bounds().fill(Color::rgb(20, 150, 125))
        })
    }).build()?;
    let options = RenderOptions::default().limits(RasterLimits {
        max_work: 1,
        ..RasterLimits::sandbox()
    });
    match render_still(&timeline, Time::ZERO, &options) {
        Ok(_) => println!("frame accepted"),
        Err(error) => eprintln!("frame rejected: {error}"),
    }
    Ok(())
}
```

上述代码中故意设置的微小计算量上限仅用于直观展示准入失败的防御机制，绝非优化建议。触发准入超额拒绝本身也是一种合法的计算结论，绝不可将其当作单帧渲染耗时。

## 预算分层体系

| 控制边界 | 约束的维度与含义 |
| --- | --- |
| `ValidationLimits` | 输入复杂度控制，如节点总数、树嵌套深度、绘制指令数 |
| `RasterLimits` | 光栅化像素总量、活跃逻辑字节、光栅化计算工作量配额 |
| `ResourceStore` / `RenderCache` | 长期常驻的逻辑内存与缓存条目数量上限 |
| `ExportOptions.max_parallel_bytes` | 允许多个并发导出渲染槽位同时占用的总显存配额 |
| Studio 视口帧 LRU 缓存 | 仅用于最终呈现画面的缓存保留，不同于渲染器内部工作集 |

默认的 `RasterLimits::authoring()` 不设工作量上限，但依然严格核验像素总数与活跃字节数。`sandbox()` 开启显式的 2 亿工作量单位上限。这两者均不是物理超时定时器，不是操作系统进程 RSS 内存沙箱，更无法充当限制 Rust 原生回调的隔离沙箱。

超大尺寸的半透明图层、模糊光晕、高分辨率位图、密集排版文本与粒子、运动模糊采样以及超大输出分辨率均会显著拉高资源开销。隐藏在不可见分支下的无效几何依然会被严格校验；设置 `opacity = 0` 无法绕过损坏的结构。

## 首先定位瓶颈所处的阶段

在着手优化之前，必须首先固定短片、时刻、分辨率、画质模式、资产、字体、渲染后端与预算配额，随后按序排查性能损耗究竟发生在哪个环节：

1. **创作求值与编译阶段**：静态不变的内容是否被无谓地重复重建？`context.memo` 是否被正确使用？
2. **覆盖率 / 排版 / 材质准备阶段**：是否被冷启动未命中缓存所主导？随机 Seek 与单帧重复重放的耗时差异有多大？
3. **CPU/GPU 图层合成阶段**：滤镜数量、图层层数与实际像素填充率发生了怎样的变化？
4. **输出与回读阶段**：是否在无需内存像素的场合错误请求了 CPU 内存帧而非外部显存纹理？
5. **编码 / 磁盘 I/O / 界面呈现阶段**：是否将视频流式编码、时间轴回放调度或桌面窗口垂直同步等待误算成了渲染耗时？

单凭一个笼统的 FPS 帧率绝对无法同时回答上述五个问题。GPU 命令提交耗时并不等于 GPU 实际完成耗时，在 CPU 侧用墙钟测量 submit 到 finish 的时间差绝不能替代 GPU 底层硬件时间戳查询。

## 基准测试工具选型

| 测试目标 | 核心回答的技术问题 |
| --- | --- |
| `performance` | 对已固化的参考测试组，严密验证某项针对性优化是否具有因果层面的加速收益 |
| `films` | 评估实际的 Gallery 完整示范短片的真实渲染耗时与吞吐量 |
| `criterion_frames` | 针对少数热身状态下的 CPU 全帧工作负载进行快速的统计学观测 |
| `breadth` | 详尽剖析跨内容类型、分辨率、流水线阶段与图元的微观开销特征 |

在需要时可在仓库中执行以下命令：

```sh
cargo bench --locked --offline -p motion-bench --no-default-features --features text,particles --bench criterion_frames
cargo bench --locked --offline -p motion-bench --bench breadth
cargo bench --locked --offline -p motion-bench --bench films --features films,gpu
```

上述命令会实际编译并测量真实负载，查阅文档本身不执行任何命令。测试详情见[基准测试指南](../benchmarks.md)。

## 性能优化宣称的数据凭证要求

针对某一工作负载进行对照组与候选组比对时，必须严格控制字体、特性开关、机器硬件/编译器版本、图形适配器、画质等级、分辨率、预算配额与采样参数完全一致。固化源码与可执行文件版本，验证生成图像与 Seek 定位重放位完全一致，并在独立的进程中以 AB/BA 交替顺序配对测量。

报告必须详细记录每个用例的 P50 中位数、在充足样本下的 P95 分位数、各次运行间的离散度（MAD）以及统计不确定性置信区间。批次测试的 P95 绝不能直接叫作单帧长尾时延；过期的历史报告不能代表当前源码或修订后的默认预算基线。

[当前实测数据](../benchmarks.md#当前实测数据)完整包含了源码 Git 版本信息与原始数据。它们绝不代表对所有业务内容的实时帧率承诺，也严禁将不同工作负载的加速比简单平均化为一个虚浮的整体倍率。

## 错误分类与确定性重放

`motion::Error` 完整保留错误分类、发生帧号与底层原因。在代码中请通过 `kind`、`frame` 并结合 `downcast_ref` 进行强类型模式匹配，而非依赖固定的文本描述。

同步回调中的 panic 属于受信任 Rust 代码内部的 panic；跨越后台工作线程边界时会被安全捕获并转换为场景 panic 诊断。自动回退重试仅适用于被明确许可的显存配额超限场景，对于代码 panic、非有限浮点数或计算量超标一律直接报错。

确定性重放必须建立在固定的输入之上，包含随机种子、字体字节、外部资源环境与精确时间 ticks。请严格按照 A、B、再 A 的顺序检验像素重放一致性。请遵循已声明的 CPU/GPU 视觉容差，切勿假设所有显卡驱动上的浮点光栅化行为逐比特完全一致。

字体选择与哈希报告仅用于源码层面的精准审计，不保证跨平台的字形光栅化像素绝对一致。延迟加载的音频或图片文件在短片导出期间严禁被外部进程篡改。

## 质量验证策略

针对小型修改，应当先从狭窄的行为或边界测试入手，随后逐步覆盖受影响的特性组合矩阵。针对纯几何数学与时钟逻辑编写属性测试；针对内容系统检验主体可见性与精确重放；针对音频系统检验实际解码采样点；针对视频系统校验解码后的准确帧数、PTS 时间戳与容器元数据。

编译通过、被忽略的测试固件或无测试用例匹配的空过滤器绝不代表通过了运行时验收。桌面窗口交互、真实物理声卡以及跨平台显卡驱动崩溃恢复需要单独验收。单元测试与性能基准测试服务于截然不同的质量结论。

## 常见踩坑点

- 混淆逻辑峰值内存、空闲对象池、外部强引用与系统物理 RSS 内存。
- 为了片面追求跑分，在未公开说明的情况下擅自调低画面精度、替换字体、降低画质或放大预算。
- 仅仅对同一个热身帧反复测速，便盲目宣称在随机 Seek 或冷启动下同样具备高帧率。
- 误将触发默认预算拒绝的瞬间当作渲染耗时，或把并发工作线程数误判为实际处理吞吐量。
- 假定结构化校验能够自动拦截 Rust 用户回调内部的慢速磁盘 I/O 或死循环。
